## 0. 概念速查

动手前先建立这几个概念，后面配置就不会一头雾水。

### Workers 是什么

不是"工作区"。名字来自浏览器的 **Service Worker** —— 一段拦截并处理 HTTP 请求的脚本。CF Workers 就是把这个模型搬到了全球边缘节点。

```
传统服务器 (linux-C)              Cloudflare Workers
┌────────────────────┐            ┌────────────────────┐
│  完整 Linux 系统    │            │  V8 isolate 沙箱   │  ← Chrome 的 JS 引擎
│  ├ 进程常驻         │            │  ├ 请求来才活      │
│  ├ 监听 :8000       │            │  ├ 无端口概念      │
│  ├ 有文件系统       │            │  ├ 无文件系统      │
│  └ 想装啥装啥       │            │  └ 只有 JS/WASM    │
└────────────────────┘            └────────────────────┘
     启动 秒级                          启动 <5ms
```

Worker 没有 `app.listen(8000)`，只有一个 `fetch` 函数。边缘节点收到请求就调它，返回一个 `Response`。整个心智模型就这么大。

| 对比项 | linux-C | Workers |
| --- | --- | --- |
| 语言 | 任意 | JS / TS / Python(WASM) / Rust(WASM) |
| 文件系统 | 有 | 无，用 R2 / KV 替代 |
| 监听端口 | 有 | 无，事件驱动 |
| 长驻进程 / 后台任务 | 有 | 无（用 Cron Triggers / Queues） |
| CPU 时间 | 无限 | 免费版 10ms/请求，付费 30s |
| 冷启动 | 秒级 | <5ms |

### 绑定（Bindings）

Workers 最核心的设计。资源不通过连接字符串获取，而是在配置里声明，运行时由平台注入。

```
传统方式                          Workers 绑定
────────────────                 ────────────────
连接字符串写在 appsettings        在 wrangler.jsonc 声明 binding
new SqlConnection(connStr)        直接用 env.DB
走网络 TCP 连数据库                运行时注入，无连接字符串、无密码
密码可能泄露到 git                 凭据根本不存在于代码里
```

### 产品全家桶

| 产品 | 定位 | 类比 |
| --- | --- | --- |
| **Workers** | 边缘函数运行时 | 应用服务器 |
| **Static Assets** | 静态文件托管 | nginx 的 root |
| **D1** | SQLite 数据库 | 轻量 SQL Server |
| **KV** | 全球键值存储，读快写慢（最终一致） | Redis（但不能当锁） |
| **R2** | 对象存储，**出站流量免费** | S3 / 腾讯云 COS |
| **Durable Objects** | 强一致有状态对象 | 单例服务 + 锁 |
| **Queues** | 消息队列 | RabbitMQ |
| **Cron Triggers** | 定时任务 | crontab |
| **Hyperdrive** | 连接外部 PG/MySQL 的连接池 | 数据库中间件 |

### Static Assets 的路由规则

```
请求进来
  ├─ 匹配到静态文件？ → 返回文件
  └─ 没匹配到        → 交给 Worker（前提是配了 main）
```

两个反直觉的点，都是实测确认的：

- `not_found_handling: "single-page-application"` **在有 Worker 时不会自动兜底**，Worker 必须自己调 `env.ASSETS.fetch(request)`
- `/api/*` **不需要** `run_worker_first` 就能正确进 Worker

### Zone 级 vs Worker 级功能

**这个区分很重要**，决定了哪些功能现在能用、哪些要等域名接入。

| 类别 | 功能 | 需要域名接入 CF？ |
| --- | --- | --- |
| **Worker 级** | Workers、D1、KV、R2、Cron、Secrets、Rate Limiting binding、Logs | ❌ 不需要，注册账号即可 |
| **Zone 级** | WAF、缓存规则、Bot 防护、页面规则、Analytics、自定义域名 | ✅ 必须先做流程 2 |

所以本方案的阶段 A~C、D 都不依赖域名，`workers.dev` 子域就够用。

## 1. 前置说明

### 1.1 项目放哪

建议放 **WSL 原生文件系统**，不要放 `/mnt/f`：

```bash
~/projects/cf-lab
```

原因：WSL 访问 `/mnt/*` 走 9p 协议，`npm install` 会慢 5~10 倍，`vite dev` 的文件监听也不灵。

Windows 侧要编辑的话两条路：

- VS Code 装 **Remote - WSL** 扩展，`code ~/projects/cf-lab` 直接打开（推荐）
- 资源管理器输入 `\\wsl$\Ubuntu\home\fengyuan\projects\cf-lab`

> 本项目是纯 Node，不涉及 .NET，所以 CLAUDE.md 里"必须用 cmd.exe"的规则**不适用**，全程在 WSL 里做。

### 1.2 会不会扣钱

不会。没绑信用卡的账号就是 Workers Free 计划，**超额直接限流，不会自动扣费**。

| 资源 | 免费额度 | 本项目消耗 |
| --- | --- | --- |
| Workers 请求 | 10 万/天 | 个位数 |
| Workers CPU | 10 ms/请求 | 用不到 1ms |
| D1 存储 | 5 GB | 几 KB |
| D1 读 | 500 万行/天 | 忽略 |
| KV 读 | 10 万/天 | 忽略 |

唯一注意：**R2 需要绑卡才能开通**（即使在免费额度内）。阶段 E 可选，不想绑卡就跳过。

### 1.3 阶段划分

| 阶段 | 内容 | 耗时 | 产物 |
| --- | --- | --- | --- |
| A | 跑通第一个 Worker | 15 min | 一个能访问的 `*.workers.dev` |
| B | 正式项目骨架：Vue + Workers 一体 | 30 min | 前后端同域的空壳 |
| C | D1 数据库 + 留言板 API | 45 min | 功能完整的站 |

| E | 存储扩展（可选） | 30 min | KV / R2 |

## 2. 阶段 A · 跑通第一个 Worker

目的只有一个：建立"**本地写代码 → 一条命令 → 全球 300 个节点**"的直观感受。这一步的项目用完就删。

### 2.1 安装与登录

```bash
mkdir -p ~/projects && cd ~/projects

# 装 wrangler（CF 官方 CLI，一切操作的入口）
npm install -g wrangler
wrangler --version

# 登录
wrangler login
```

`wrangler login` 会打开浏览器授权。WSL 下如果没自动弹窗，它会在终端打印一个 URL，复制到 Windows 浏览器打开即可（回调地址 `localhost:8976`，WSL2 与 Windows 的 localhost 互通，能正常回调）。

**OAuth 走不通的退路**：CF 后台 → 右上角头像 → API Tokens → 用 "Edit Cloudflare Workers" 模板生成，然后：

```bash
export CLOUDFLARE_API_TOKEN=你的token
```

验证：

```bash
wrangler whoami
```

### 2.2 起一个最小 Worker

```bash
npm create cloudflare@latest cf-hello -- \
  --type=hello-world --lang=ts --no-git --no-deploy --no-agents
```

> ⚠️ **`--no-agents` 必须加**。不加的话 C3 跑到最后会弹一个交互提问
> "Do you want to add an AGENTS.md file?"，在非交互环境下会卡死并中断，
> 导致 `wrangler.jsonc` 里残留 `<WORKER_NAME>` / `<COMPATIBILITY_DATE>` 占位符。
> 真被打断了也不用重来 —— 模板文件和依赖其实都装好了，手动把两个占位符替换掉即可。

看核心文件：

```bash
cd cf-hello
cat src/index.ts
cat wrangler.jsonc
```

`src/index.ts` 就是全部逻辑：

```ts
export default {
	async fetch(request, env, ctx): Promise<Response> {
		return new Response("Hello World!");
	},
} satisfies ExportedHandler<Env>;
```

**整个 Worker 就是一个默认导出对象，里面有个 `fetch` 方法。** 没有 `app.listen()`，没有路由表，没有中间件栈。

三个参数：

| 参数 | 是什么 | 对比 Node |
| --- | --- | --- |
| `request` | **标准 Web Request 对象** | 不是 Node 的 `req`，是浏览器 `fetch()` 里那个 Request |
| `env` | 所有绑定的集合 | 相当于依赖注入容器。加了 D1 后 `env.DB` 就在这 |
| `ctx` | 执行上下文 | 主要用 `ctx.waitUntil()` 做「响应已返回、后台继续干活」 |

**关键认知：Workers 用的是 Web 标准 API，不是 Node API。**

```js
✅ fetch() / Request / Response / URL / crypto.subtle / TextEncoder
❌ require('fs') / require('http') / process.env / __dirname
```

这就是为什么需要 `compatibility_flags: ["nodejs_compat"]` —— 那是给依赖 Node API 的 npm 包开的兼容层。

### 2.3 本地跑 + 部署

```bash
npx wrangler dev
# 浏览器打开 http://localhost:8787
```

> `wrangler dev` 不是在 Node 里跑，是在本地启了一个 **workerd** —— 和 CF 生产环境完全一样的运行时。本地能跑通，线上基本就能跑通。

```bash
npx wrangler deploy
```

输出里会给你 `https://cf-hello.<你的子域>.workers.dev`。用手机流量访问一下 —— 这就是全球部署了。

**阶段 A 完成。** 从零到全球可访问不到 15 分钟，没碰过服务器、防火墙、nginx。

清理（可选）：

```bash
cd ~/projects && npx wrangler delete --name cf-hello
```

## 3. 阶段 B · 正式项目骨架

用 C3 的 Vue 模板，它会自动配好 `@cloudflare/vite-plugin` —— 这个插件让 `vite dev` 直接在 workerd 里跑 Worker，前后端一个端口，不用配 proxy。

> **现状说明**：CF 从 2025 年起新项目推荐用 **Workers + Static Assets**，Pages 已进入维护模式。所以不用 Pages，前端静态文件和 API 放在同一个 Worker 里。

### 3.1 创建项目

```bash
cd ~/projects
npm create cloudflare@latest cf-lab -- \
  --framework=vue --platform=workers --lang=ts \
  --no-agents --no-git --no-deploy
```

全部用参数指定，不会卡在任何交互提问上。C3 会自动做一件好事：

```
├ Selecting workerd compatibility date
│ compatibility date 2026-08-31        ← 自动选了本地 workerd 支持的日期
```

生成后的结构（**注意 Worker 在 `server/`，不是 `worker/`**）：

```
cf-lab/
├── src/                       ← Vue 前端（vite build 后进 dist/client）
│   ├── App.vue
│   ├── router/
│   ├── views/                 HomeView / AboutView
│   └── components/
├── server/                    ← Worker 后端
│   └── index.ts
├── public/                    ← 不经打包、原样复制的静态文件
├── vite.config.ts             ← 关键：cloudflare() 插件在这
├── wrangler.jsonc             ← CF 配置
└── worker-configuration.d.ts  ← wrangler types 自动生成的 Env 类型
```

`vite.config.ts` 里的关键一行：

```ts
import { cloudflare } from "@cloudflare/vite-plugin"

export default defineConfig({
	plugins: [vue(), vueDevTools(), cloudflare()],   // ← cloudflare() 让 vite dev 在 workerd 里跑 Worker
})
```

**这个插件的价值**：`npm run dev` 时前端和 Worker 在同一个端口（5173），没有跨域、不用配 proxy，且本地开发用的就是生产同款 workerd 运行时。

`package.json` 的四条脚本：

| 命令 | 做什么 | 什么时候用 |
| --- | --- | --- |
| `npm run dev` | Vite + workerd 一体，热更新 | **日常开发** |
| `npm run preview` | build 后用 wrangler dev 跑 | 上线前模拟生产 |
| `npm run deploy` | build + wrangler deploy | 发布 |
| `npm run cf-typegen` | 读 `wrangler.jsonc` 生成 `Env` 类型 | **每次加/改绑定后必跑** |

`cf-typegen`（等价于 `npx wrangler types`）值得单独记：加了 D1 绑定后跑一次，TS 里 `env.DB` 就有完整类型提示。**配置驱动类型**，改了配置不重跑就没类型。

### 3.2 装 Hono

在 Workers 上写 API 的事实标准，用法几乎和 Express 一样，体积只有 14KB：

```bash
npm install hono
```

### 3.3 配置 wrangler.jsonc（最关键的一步）

C3 的 Vue 模板生成的配置长这样，**注意 Worker 入口是 `server/index.ts`**：

```jsonc
{
	"$schema": "node_modules/wrangler/config-schema.json",
	"name": "cf-lab",
	"compatibility_date": "2026-08-31",
	"main": "server/index.ts",
	"assets": {
		"not_found_handling": "single-page-application",
		"binding": "ASSETS"          // ← 这行要手动加，见下方「SPA 路由陷阱」
	},
	"observability": { "enabled": true },
	"upload_source_maps": true
}
```

逐字段解释 —— **这几个字段理解了，Workers 就懂一半了**：

| 字段 | 作用 |
| --- | --- |
| `main` | Worker 入口文件（Vue 模板里是 `server/index.ts`） |
| `compatibility_date` | 运行时版本锁。**必须 ≤ 本地 workerd 支持的日期**（见下方说明），定了就别动 |
| `assets.directory` | 前端打包产物目录。**用 `@cloudflare/vite-plugin` 时不用写**，插件构建时自动注入 `../client` |
| `assets.not_found_handling` | `single-page-application` = 资源未命中时返回 `index.html`。**但有 Worker 时不会自动生效**，见下 |
| `assets.binding` | 把静态资源服务注入成 `env.ASSETS`，Worker 里可以主动去取 |
| `observability` | 开启日志，阶段 D 要用 |
| `upload_source_maps` | 线上报错能定位到 TS 源码行号，而不是压缩后的乱码 |

> **`compatibility_date` 怎么填**：不是「今天的日期」，而是**「这份代码按哪一天的运行时行为编写」**。CF 不断修改运行时行为（修 bug、改默认值、换 API 语义），每次变更都挂在一个日期后面，靠这个字段保证老代码不被改坏。
>
> 填的日期**必须 ≤ 本地 workerd 支持的最大日期**，否则 `wrangler dev` 直接报
> `Compatibility date "xxx" is in the future and unsupported`。
>
> 查本地支持到哪天：
>
> ```bash
> node -p "require('./node_modules/workerd/package.json').version"
> # 输出 1.20260831.1  →  中间那串就是最大支持日期 2026-08-31
> ```
>
> 最省事的做法：**让 C3 脚手架自己填，别手动改**。

#### ⚠️ SPA 路由陷阱（实测确认，官方 Vue 模板开箱即中）

Static Assets 的真实路由规则是：

```
请求进来
  ├─ 匹配到静态文件？ → 返回文件           （/、/assets/*.js 走这条）
  └─ 没匹配到        → 交给 Worker        （/api/、/about 走这条）
                        Worker 返回啥就是啥
```

**关键：`not_found_handling` 在配置了 Worker（`main`）的情况下不会自动兜底。**

官方 Vue 模板的 Worker 兜底是这样写的：

```ts
return new Response(null, { status: 404 });   // ← 所有非 /api/ 请求都被它 404 掉
```

结果就是**自带的 `/about` 路由开箱即 404**，dev 和生产构建行为一致。

修法两步：

1. `wrangler.jsonc` 的 `assets` 里加 `"binding": "ASSETS"`
2. Worker 兜底改成把请求还给静态资源服务：

```ts
export default {
	fetch(request, env) {
		const url = new URL(request.url);

		if (url.pathname.startsWith("/api/")) {
			return Response.json({ name: "Cloudflare" });
		}

		// 非 API 请求交还给静态资源服务。
		// 配合 not_found_handling: "single-page-application"，
		// 找不到的路径会返回 index.html，由 vue-router 接管。
		return env.ASSETS.fetch(request);
	},
} satisfies ExportedHandler<Env>;
```

改完记得跑 `npx wrangler types` 重新生成 `Env` 类型，`env.ASSETS` 才有类型提示。

验证（生产构建下实测）：

| 路径 | 修复前 | 修复后 |
| --- | --- | --- |
| `/` | 200 html | 200 html |
| `/api/` | 200 json | 200 json |
| `/about` | **404** | **200 html** ✅ |

> 附带说明：**不需要 `run_worker_first`**。实测 `/api/` 在默认配置下就能正确返回 JSON，不会被 SPA 规则吃掉。这个字段只在你需要「Worker 抢在静态资源之前处理某些路径」时才用得上（例如给静态资源本身加鉴权）。

### 3.4 跑起来

```bash
npm run dev
```

## 4. 阶段 C · D1 数据库 + 留言板 API

### 4.1 建库

```bash
npx wrangler d1 create cf-lab-db --location=apac --binding=DB
```

**这两个参数都不是可选的，缺一个就要返工。**

#### ⚠️ 坑一：不指定 `--location`，数据库会被放到代理出口所在的区域

不加 `--location` 时，CF 按**创建请求的来源 IP** 决定主库位置。如果你开着代理（Clash / VPN），它看到的是代理出口：

```
✅ Successfully created DB 'cf-lab-db' in region WNAM    ← 美国西部，不是你想要的
```

D1 是**单主库 + 可选只读副本**的架构，**所有写入都必须回到主库**：

| 主库区域 | 从广东写一条数据 |
| --- | --- |
| WNAM（美西） | 约 600 ms+ |
| APAC（亚太） | 约 60~120 ms |

`--location` 是显式指令，**不受代理影响**。可选值：`weur` `eeur` `apac` `oc` `wnam` `enam`。

建完用这条命令核对：

```bash
npx wrangler d1 info cf-lab-db
# 看 running_in_region 那一行
```

#### ⚠️ 坑二：不指定 `--binding`，绑定名会是丑陋的下划线形式

wrangler 默认按数据库名生成绑定名 `cf_lab_db`，代码里就得写 `env.cf_lab_db`。惯例是 `DB`。

#### 交互提问怎么答

不带 `--update-config` 时会问两个问题：

| 提问 | 建议 | 原因 |
| --- | --- | --- |
| Would you like Wrangler to add it on your behalf? | 都行 | 自动写入很方便，但要检查写对没有 |
| For local dev, connect to the **remote** resource instead of local? | **no** | 见下 |

第二问答 `yes` 会在配置里加一行 `"remote": true`，含义是**本地开发直接连线上数据库**：

| | `remote: true` | 本地模式（推荐） |
| --- | --- | --- |
| 数据 | 本地线上同一份 | 本地一份独立 SQLite |
| 速度 | 每次查询走公网到主库 | 毫秒级 |
| 配额 | 消耗真实免费额度 | 不消耗 |
| 误操作 | **`DROP TABLE` 直接删线上数据** | 删了重建即可 |

#### ⚠️ 坑三：删库重建后，配置文件里的旧条目不会自动清理

如果你像上面这样发现区域错了、删掉重建，`wrangler.jsonc` 里会**同时留下两条** `d1_databases` 记录 —— 一条指向已删除的库。部署时会报数据库不存在。**手动删掉失效那条。**

最终配置应该长这样：

```jsonc
"d1_databases": [
	{
		"binding": "DB",                                        // 代码里用 env.DB
		"database_name": "cf-lab-db",
		"database_id": "<DATABASE_ID>"   // 只对 --remote 有意义
	}
]
```

改完记得重新生成类型：

```bash
npx wrangler types
grep "DB:" worker-configuration.d.ts     # 应该看到 DB: D1Database;
```

### 4.3 写 API（Hono 版）

把手写的 `if (url.pathname.startsWith(...))` 换成声明式路由：

```ts
import { Hono } from "hono";

// Env 类型由 `wrangler types` 从 wrangler.jsonc 自动生成，
// 里面已经有 DB: D1Database 和 ASSETS: Fetcher。
const app = new Hono<{ Bindings: Env }>();

interface Message {
	id: number;
	nickname: string;
	content: string;
	created_at: string;
}

/** 列表：最新 50 条 */
app.get("/api/messages", async (c) => {
	const { results } = await c.env.DB.prepare(
		`SELECT id, nickname, content, created_at
		   FROM messages
		  ORDER BY id DESC
		  LIMIT 50`,
	).all<Message>();

	return c.json(results);
});

/** 发布 */
app.post("/api/messages", async (c) => {
	let body: { nickname?: string; content?: string };
	try {
		body = await c.req.json();
	} catch {
		return c.json({ error: "请求体不是合法 JSON" }, 400);
	}

	const nickname = body.nickname?.trim();
	const content = body.content?.trim();

	if (!nickname || !content) {
		return c.json({ error: "昵称和内容不能为空" }, 400);
	}
	if (nickname.length > 20) {
		return c.json({ error: "昵称最多 20 字" }, 400);
	}
	if (content.length > 500) {
		return c.json({ error: "内容最多 500 字" }, 400);
	}

	// .bind() 是参数化查询，防 SQL 注入。永远不要拼字符串。
	const row = await c.env.DB.prepare(
		`INSERT INTO messages (nickname, content)
		 VALUES (?, ?)
		 RETURNING id, nickname, content, created_at`,
	)
		.bind(nickname, content)
		.first<Message>();

	return c.json(row, 201);
});

/** 删除 */
app.delete("/api/messages/:id", async (c) => {
	const id = Number(c.req.param("id"));
	if (!Number.isInteger(id) || id <= 0) {
		return c.json({ error: "id 非法" }, 400);
	}

	const { meta } = await c.env.DB.prepare("DELETE FROM messages WHERE id = ?")
		.bind(id)
		.run();

	if (meta.changes === 0) {
		return c.json({ error: "留言不存在" }, 404);
	}
	return c.body(null, 204);
});

/** 探活：顺便暴露处理请求的边缘机房，方便观察调度 */
app.get("/api/health", (c) => {
	const cf = c.req.raw.cf as { colo?: string; country?: string } | undefined;
	return c.json({
		ok: true,
		colo: cf?.colo ?? null,
		country: cf?.country ?? null,
		time: new Date().toISOString(),
	});
});

/**
 * 兜底：非 API 请求交还给静态资源服务。
 * 配合 not_found_handling: "single-page-application"，
 * 未命中的路径返回 index.html，由 vue-router 接管。
 */
app.all("*", (c) => c.env.ASSETS.fetch(c.req.raw));

export default app;
```

#### 三个要点

**① 路由顺序很重要**

`app.all("*")` 这条兜底必须放在**所有 API 路由之后**。Hono 按注册顺序匹配，放前面会把所有请求都吞掉。

**② D1 的三个终结方法别用混**

| 方法 | 返回 | 用在哪 |
| --- | --- | --- |
| `.all<T>()` | `{ results: T[] }` | 查列表 |
| `.first<T>()` | `T \| null` | 查单条 |
| `.run()` | `{ meta }` | 增删改，`meta.changes` 是影响行数 |

**③ `.bind()` 是参数化查询，永远别拼字符串**

和 SqlSugar 的参数化是一回事，防 SQL 注入。

另外插入用了 `RETURNING`：

```sql
INSERT INTO messages (nickname, content) VALUES (?, ?)
RETURNING id, nickname, content, created_at
```

SQLite 支持这个语法，**一次往返就拿到插入后的完整行**，不用再查一次。主库在 APAC，省一次往返就是省几十毫秒。

Worker 级，不需要域名：

代码里用：

```ts
app.use('/api/*', async (c, next) => {
  const ip = c.req.header('CF-Connecting-IP') ?? 'unknown'

## 7. 绑定自定义域名

`*.workers.dev` 有两个硬伤：域名难看，**而且在中国大陆访问不了**。绑自己的域名能解决第二个（速度解决不了，见姊妹文档）。

**前提**：域名已接入 Cloudflare 且 zone 状态为 **Active**（见《Cloudflare 实战经验与踩坑记录》的流程 2）。

### 两种绑定方式，别搞混

| 方式 | 配置写法 | 含义 |
| --- | --- | --- |
| **Custom Domain** | `{ "pattern": "lab.example.com", "custom_domain": true }` | **整个主机名归 Worker**。CF 自动建 DNS 记录、自动签证书 |
| **Route** | `{ "pattern": "example.com/api/*" }` | Worker **拦截符合模式的路径**，其余照常回源。要求该主机名已有橙云记录 |

第二种是「边缘胶水层」的典型用法 —— 主站还在你自己的服务器上，但 `/api/*` 被 Worker 截走。

### 配置

```jsonc
"routes": [
	{ "pattern": "lab.example.com", "custom_domain": true }
]
```

然后 `npm run deploy`。CF 自动完成三件事：

```
1. 在 zone 里创建该主机名的 DNS 记录（橙云 A + AAAA）
2. 申请并签发证书（Google Trust Services，90 天，自动续期）
3. 把该主机名的全部流量绑到这个 Worker
```

> ⚠️ 证书签发要一两分钟。部署成功后立刻访问可能报 SSL 错误，等一会儿即可。

### ⚠️ 副作用：`workers.dev` 会被自动禁用

部署时会看到：

```
▲ [WARNING] Because 'workers_dev' is not in your Wrangler file,
   it will be disabled for this deployment by default.
```

之后访问 `xxx.workers.dev` 会返回 **404 / error code 1042**。

**这是好的默认值**，而不是 bug —— 生产环境本来就该关掉 `workers.dev`，否则别人绕过你的域名直接访问它，能躲掉你在 zone 上配的 WAF 和缓存规则。

想保留的话加一行 `"workers_dev": true`，但**不建议**。

### 白捡的三样东西

| | 说明 |
| --- | --- |
| **IPv6** | CF 自动给 AAAA 记录，源站没有 IPv6 也能被 IPv6-only 用户访问 |
| **证书全托管** | 90 天自动续，不需要 certbot、不需要续期 timer、不需要证书路径配置 |
| **源站 IP 隐藏** | 解析到 CF Anycast IP，扫描器看不到真实服务器 |

### 验证清单

```bash
# DNS 是否指向 CF Anycast
curl -s "https://cloudflare-dns.com/dns-query?name=lab.example.com&type=A" \
  -H "accept: application/dns-json" | python3 -m json.tool

# 证书

  | openssl x509 -noout -subject -issuer -dates

# 路由与接口

| 坑 | 现象 | 解 |
| --- | --- | --- |
| 项目放在 `/mnt/f`（WSL 挂载盘） | `npm install` 慢 5~10 倍、热更新不触发 | 放 WSL 原生路径 `~/projects` |
| `compatibility_date` 填了未来日期 | `wrangler dev` 报 `Compatibility date "xxx" is in the future and unsupported` | 填 ≤ 本地 workerd 版本的日期，用 `node -p "require('./node_modules/workerd/package.json').version"` 查；最省事是让 C3 自动填 |
| C3 脚手架卡在 `AGENTS.md` 提问 | 命令被打断，`wrangler.jsonc` 残留 `<WORKER_NAME>` / `<COMPATIBILITY_DATE>` 占位符 | 加 `--no-agents`；已被打断的话手动替换占位符，其余文件和依赖其实已生成完毕 |
| SPA 路由 404（如 `/about`） | 官方 Vue 模板的 Worker 兜底直接返回 404，`not_found_handling` 不生效 | 加 `assets.binding: "ASSETS"`，Worker 兜底改成 `return env.ASSETS.fetch(request)`，见 3.3 |
| D1 建在了错误的区域 | `created DB in region WNAM`，从国内每次写入 600ms+ | 建库时显式 `--location=apac`；不加的话按**代理出口 IP** 判断区域 |
| D1 绑定名很丑 | 代码里要写 `env.cf_lab_db` | 建库时加 `--binding=DB` |
| 删库重建后配置残留 | 部署报数据库不存在 | 手动删掉 `wrangler.jsonc` 里指向已删除库的那条 `d1_databases` |
| D1 migration 只跑了 `--local` | 本地全绿，线上报 `no such table` | `--local` 和 `--remote` 是两个独立数据库，各跑一次 |
| 改了绑定没重新生成类型 | TS 里 `env.DB` 报未定义 | `npx wrangler types` |
| `wrangler login` 在 WSL 弹不出浏览器 | 卡住 | 复制终端 URL 手动打开；回调走 `localhost:8976`，确认 `no_proxy` 含 `127.*` 和 `localhost` |
| 用了 Node 专有 API 没开 `nodejs_compat` | 部署报错找不到模块 | `compatibility_flags: ["nodejs_compat"]` |
| CPU 超 10ms | 免费版报 `Exceeded CPU limit` | 别在 Worker 里做重计算。注意是 **CPU 时间**不是墙钟时间，等 I/O 不算 |
| D1 当高频写库用 | 写入慢 | D1 适合读多写少；高频写用 Durable Objects |
| 加了 `routes` 后 `workers.dev` 打不开 | 404 / error code 1042 | 预期行为，是安全默认值。要保留加 `"workers_dev": true`（不建议） |
| 在 `workers.dev` 上找 WAF / 缓存规则 | 找不到入口 | Zone 级功能，必须先把域名接入 CF |
| 时间显示差 8 小时 | D1 的 `datetime('now')` 是 UTC | 前端 `new Date(s.replace(' ','T')+'Z')` 再转本地 |

## 9. 命令速查

```bash
# ---- 账号 ----
wrangler login                          # 登录（OAuth）
wrangler whoami                         # 当前账号 + token 权限清单
wrangler logout

# ---- 项目 ----
npm create cloudflare@latest <name> -- --framework=vue --platform=workers \
  --lang=ts --no-agents --no-git --no-deploy
npm run dev                             # 本地开发（Vite + workerd）
npm run build                           # 构建前端
npm run deploy                          # build + deploy
npx wrangler types                      # 由 wrangler.jsonc 生成 Env 类型（改绑定后必跑）
npx wrangler deploy --dry-run           # 只打包不上传，检查配置
npx wrangler delete --name <n>          # 删除 Worker
npx wrangler versions list              # 部署历史
npx wrangler rollback                   # 回滚

# ---- D1 ----
npx wrangler d1 create <db> --location=apac --binding=DB
npx wrangler d1 list
npx wrangler d1 info <db>               # 看 running_in_region / 用量
npx wrangler d1 delete <db>
npx wrangler d1 migrations apply <db> --local
npx wrangler d1 migrations apply <db> --remote
npx wrangler d1 execute <db> --remote --command "SELECT 1"
npx wrangler d1 execute <db> --remote --json --command "..."   # 干净的 JSON 输出
npx wrangler d1 execute <db> --remote --file=./query.sql

# ---- 日志 ----
npx wrangler tail                       # 实时日志
npx wrangler tail --status error

# ---- 密钥 ----
npx wrangler secret put <KEY>
npx wrangler secret list
npx wrangler secret delete <KEY>

# ---- KV ----
npx wrangler kv namespace create <name>
npx wrangler kv key put --binding=KV "k" "v" --remote
npx wrangler kv key get --binding=KV "k" --remote
```

### 没有 dig 时怎么查 DNS

WSL 默认不装 `dnsutils`，而且 Clash TUN 模式下 `nslookup` 只会返回 `198.18.x.x` 的 fake-ip。用 DoH 查真实解析：

```bash
curl -s -H "accept: application/dns-json" \
  "https://dns.alidns.com/resolve?name=example.com&type=A" | python3 -m json.tool
```

换 `https://cloudflare-dns.com/dns-query` 或 `https://dns.google/resolve` 可以从不同视角看传播情况。

查注册局的权威 NS（判断 NS 变更有没有被接受，比查解析器可靠）：

```bash
curl -s https://rdap.org/domain/example.com | python3 -m json.tool | grep -A2 ldhName
```
